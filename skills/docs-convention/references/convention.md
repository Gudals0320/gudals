# docs 규약: 에이전트가 쓰는 문서의 종류와 수명

지휘 세션과 작업자 세션이 여러 단계에 걸쳐 일하는 저장소에서, 문서를 어디에 어떤 수명으로 두는지 정한다. 대상은 에이전트가 만드는 마크다운이다. 코드 주석과 API 문서 생성기는 다루지 않는다.

## 왜 필요한가

에이전트가 만드는 마크다운은 두 종류다. **살아 있는 문서**는 다음 세션이 읽고 현재 상태로 믿는 문서다(상시 규칙, 인계, 설계, 계획). **기록**은 어떤 작업을 지시받았고, 하면서 무엇을 생각했고, 무엇을 만들었는지 남긴 문서다. 기록은 작업자의 작업 메모리를 포함한다. 작업 메모리를 추적하면 작업자가 계획과 다르게 간 곳을 diff로 확인할 수 있으므로, 기록은 버리지 않고 git에 남긴다.

증식은 살아 있는 문서를 기록처럼 다룰 때 생긴다. 한 프로젝트의 계획 문서는 3일간 커밋 13번 동안 약 1만 2천 자에서 6만 8천 자로 늘었고 줄어든 커밋이 없었다. 단계가 끝날 때마다 "반영"이라는 이름으로 덧붙였기 때문이다. 이 규약의 초안이 있는 상태에서도 다음 단계 닫기 커밋은 계획 문서를 2,240자 더 늘렸다. 그래서 이 규약은 세 가지 장치로 선다. 살아 있는 문서에만 크기 예산을 두되 **총량** 예산을 함께 두어 옮기기로 빠져나가지 못하게 한다. 단계를 닫을 때 추가가 아니라 갱신을 하게 하되 그 절차를 스크립트가 확인한다. 지시로는 지켜지지 않는 규칙은 훅이 편집 자체를 막는다.

## 원칙

- 살아 있는 문서는 현재 상태만 담는다. 끝난 계획은 지우고, 바뀐 설계는 고쳐 쓰고, 뒤집힌 결정은 결정 로그로 옮긴다.
- 기록은 작업 단위로 git에 남기고, 작업이 끝나면 고치지 않는다. 작업 메모리도 기록이다.
- 살아 있는 문서는 기록을 진실의 출처로 가리키지 않는다. 가리키고 싶은 내용은 살아 있는 문서로 옮기고 그만큼 다른 것을 줄인다.
- 줄이는 길이 옮기는 길보다 싸야 한다. 그래서 파일별 예산과 총량 예산을 함께 둔다.

## 1. 문서의 종류와 수명

| 구분 | 종류 | 파일 | 수명 | 쓰기 규칙 |
|---|---|---|---|---|
| 살아 있음 | 상시 규칙 | `CLAUDE.md` 또는 `AGENTS.md` | 영구, 매 세션 로드 | 모든 세션이 지킬 규칙만. 특정 도구·환경 변수·명령 이름이 든 줄은 `testing.md`로, 변경 이력은 `README.md`로 보낸다. |
| 살아 있음 | 인계 | `docs/BRIEF.md` | 영구 | 왜, 무엇, 정한 것 표. 표의 행은 500자 이하, 날짜 하나만 남긴다. 결정이 바뀌면 행을 다시 쓰고 이전 문장은 지운다. |
| 살아 있음 | 설계 | `docs/ARCH.md` | 영구, 드물게 바뀜 | 프로세스 구조, 데이터 모델, 모듈 표, API 표만. 지금의 구조를 쓴다. 구현하며 정한 세부 값(픽셀, 초, 상한, 단축키)은 코드와 보고 절에만 둔다. |
| 살아 있음 | 계획 | `docs/PLAN.md` | 현재 단계와 다음 단계 | 아래 "PLAN의 구조". |
| 살아 있음 | 시험 요령 | `docs/testing.md` | 영구 | 환경 변수, 정리 순서, 도구의 함정. |
| 살아 있음 | 이 규약 | `docs/README.md` | 영구 | 이 파일. |
| 기록 | 작업 기록 | `docs/log/<작업>.md` | 작업 중 고침, 닫히면 고치지 않음 | 아래 "작업 파일". |
| 기록 | 결정 로그 | `docs/decisions.md` | 영구, 추가만 | 날짜, 결정, 이유, 뒤집은 결정. 커밋당 3,000자까지. |
| 기록 | 실험과 조사 | `docs/experiments/`, `docs/research/` | 영구 | 날짜를 적는다. 쓴 뒤에는 고치지 않는다. |

표에 없는 종류의 문서는 만들지 않는다. 필요하면 표에 줄을 먼저 추가한다.

### PLAN의 구조

PLAN은 2단계 제목이 세 개뿐이다.

```
# <프로젝트> 계획
## 지금: <작업 이름>
## 다음: <작업 이름>
## 열린 결정
```

- **지금**: 진행 중인 단계의 시나리오와 완료 기준. 다른 절을 가리킬 때는 ARCH의 절 번호만 쓴다.
- **다음**: 제목, 목표 세 줄, 완료 기준까지만. 시나리오는 그 단계를 시작할 때 쓴다.
- **열린 결정**: 아직 정하지 않은 것. 정해지면 줄을 지우고 `decisions.md`에 날짜와 함께 적는다.

단계 번호별 절, 모듈 표, API 표, 화면 요소 표는 PLAN에 두지 않는다. "끝남", "끝났다", "(P6)" 같은 완료 표시가 PLAN에 남아 있으면 검사가 실패한다. 끝난 것은 PLAN에 있을 이유가 없다.

### 작업 파일

작업 하나가 `docs/log/<작업>.md` 하나다. 작업은 지휘 세션이 지시 하나로 맡기는 단위이고, 보통 단계 하나 또는 그 한 조각이다. 이름은 `p7-sidebar.md`, `p6a-canvas.md`처럼 작업 번호와 짧은 이름이다. 세션이 아니라 작업으로 나누는 이유는 세션이 끊기고 이어지고 넘겨지기 때문이다. 한 작업에 붙은 모든 세션의 흔적이 한 파일에 순서대로 남는다.

첫 줄은 `상태: 열림` 또는 `상태: 닫힘`이고, 2단계 제목은 세 개뿐이다.

```
상태: 열림
날짜: 2026-10-31

## 지시
## 작업 기록
## 보고
```

- **지시**: 지휘 세션이 쓴다. 작업자가 읽을 시나리오와 완료 기준을 직접 넣는다. 10,000자까지다. 작업자가 시작한 뒤에는 고치지 않는다. 바뀐 지시는 작업자에게 메시지로 보내고, 작업자가 작업 기록 절에 날짜와 함께 받아 적는다.
- **작업 기록**: 작업자의 작업 메모리. 계획, 진행, 알아낸 것, 막힌 곳을 자기 형식으로 쓴다. 세션이 바뀌면 날짜와 세션 표시를 한 줄 넣고 이어 쓴다.
- **보고**: 만든 것, 계획과 다른 곳(사실만), 알려진 문제. 살아 있는 문서에 더할 내용을 제안하는 절은 두지 않는다. 작업자의 제안 목록은 지휘 세션의 할 일 목록이 되어 문서를 불린다.

작업이 끝나 합쳐지면 첫 줄을 `상태: 닫힘`으로 바꾼다. 그 뒤로는 아무도 고치지 않는다.

## 2. 어디에 두는가

- 루트에는 `README.md`와 `CLAUDE.md`(또는 `AGENTS.md`)만 둔다.
- `docs/` 바로 아래에는 1절의 파일만 둔다. 하위 폴더는 `log/`, `experiments/`, `research/` 셋뿐이다. 다른 폴더나 파일이 있으면 검사가 실패한다.
- 작업 파일은 모두 `docs/log/` 한 폴더에 둔다. 단계가 늘어도 늘어나는 곳은 여기뿐이다.

```
저장소/
├── README.md
├── CLAUDE.md
├── .githooks/pre-commit
├── .claude/settings.json      훅 설정
├── scripts/check-docs.mjs, docs-guard.mjs
└── docs/
    ├── README.md              이 규약
    ├── BRIEF.md  ARCH.md  PLAN.md  testing.md  decisions.md
    ├── log/                   p1-backend.md ... p7-sidebar.md
    ├── experiments/
    └── research/
```

## 3. 누가 무엇을 고치는가

작업 디렉터리가 `.claude/worktrees/` 아래면 작업자, 아니면 지휘 세션이다. 훅은 이 기준으로 판정한다.

- **작업자**가 고칠 수 있는 것: 자기 작업 파일의 작업 기록 절과 보고 절, 코드, 그리고 `docs/ARCH.md`의 모듈 표와 API 표에서 자기 모듈의 행. API 표 행은 "메서드 | 받는 것 → 주는 것" 한 줄이고 설명은 코드 주석에 둔다. 다른 살아 있는 문서는 훅이 편집을 거부한다.
- **지휘 세션**이 고칠 수 있는 것: 전부. 단, 닫힌 작업 파일과 `.docs-budget.json`은 훅이 거부한다. 예산 파일은 사람이 고친다.

## 4. 작업을 맡길 때

1. `docs/log/<작업>.md`를 템플릿으로 만들고 지시 절을 쓴다. 시나리오와 완료 기준을 복사해 넣는다. "PLAN 4절 J만 읽어라"는 지시는 작업자가 결국 파일 전체를 읽게 만든다.
2. 작업자가 읽을 파일은 `CLAUDE.md`, `docs/ARCH.md`, 자기 작업 파일 셋이다. PLAN과 BRIEF는 작업자가 읽지 않는다. 다른 작업 파일을 가리켜야 하면 하나만, "파일 이름 + 절 이름"으로 적는다.
3. 검사 스크립트를 돌린다(지시 절 10,000자, 제목 구조).
4. `main`에 커밋한 뒤 워크트리를 만든다. 커밋하지 않고 워크트리를 만들면 작업자에게 파일이 없다.
5. 작업자가 끝나 합쳐지면 첫 줄을 `상태: 닫힘`으로 바꾼다. 단계 닫기(5절)는 그 단계의 모든 작업이 합쳐진 뒤에 한다.

## 5. 단계를 닫을 때

한 단계에 속한 모든 작업이 `main`에 합쳐진 뒤, 지휘 세션이 한다.

1. 작업 파일들의 작업 기록 절과 보고 절을 읽는다. 계획과 다르게 간 곳의 이유를 확인한다. 작업자의 문서 수정 제안은 따르지 않는다.
2. PLAN의 `## 지금` 절을 비우고, `## 다음`의 내용을 `## 지금`으로 올린 뒤 시나리오를 채우고, 새 `## 다음`을 쓴다. `## 열린 결정`에서 정해진 줄은 지우고 `decisions.md`에 적는다.
3. ARCH에서 구현과 달라진 문장을 찾아 그 문장만 고친다. 고친 뒤 ARCH가 커졌으면 같은 커밋에서 그만큼 줄인다.
4. BRIEF의 정한 것 표에서 바뀐 결정의 행을 다시 쓴다. 이전 문장은 `decisions.md`로 간다.
5. CLAUDE.md는 모든 세션이 지켜야 할 규칙을 새로 배웠을 때만 한 줄 늘린다. 시험 요령은 `testing.md`로.
6. `node scripts/check-docs.mjs --close`를 돌린다. 이 모드는 BRIEF와 ARCH가 HEAD보다 커지지 않았는지(문장을 고쳐 쓸 여지로 BRIEF +500자, ARCH +1,000자까지 허용), 결정 로그가 3,000자 넘게 늘지 않았는지, 닫힌 작업 파일을 건드리지 않았는지까지 본다. 글자 수를 맞추려 하지 말고 틀린 문장만 고친다. PLAN은 다음 단계가 더 크면 커질 수 있으므로 예산과 세 절 구조로만 묶는다. 통과한 뒤 커밋한다.

## 6. 크기 예산과 검사

예산은 살아 있는 문서에만 둔다. 문자 수이고 공백을 포함한다.

| 파일 | 예산 |
|---|---|
| `CLAUDE.md` 또는 `AGENTS.md` | 4,000자 |
| `docs/PLAN.md` | 15,000자 |
| `docs/BRIEF.md` | 20,000자 |
| `docs/ARCH.md` | 40,000자 |
| `docs/testing.md` | 8,000자 |
| `docs/README.md` | 12,000자 |
| 살아 있는 문서 합계 | 70,000자 |

`.docs-budget.json`으로 바꿀 수 있지만 기본값의 1.5배를 넘으면 검사가 거부하고, 바뀐 예산은 출력에 표시된다. 예산을 올리는 것은 사람의 결정이다.

`scripts/check-docs.mjs`가 확인하는 것: 파일별 예산과 합계, 루트와 `docs/` 아래의 파일 구조, PLAN의 제목 구조와 완료 표시, 작업 파일의 제목 구조와 지시 절 길이, BRIEF 표 행 길이. 모드는 셋이다.

```bash
node scripts/check-docs.mjs            # 작업 트리 검사
node scripts/check-docs.mjs --staged   # 스테이지된 내용 검사 (pre-commit)
node scripts/check-docs.mjs --close    # 단계 닫기: HEAD 대비 비증가, 닫힌 파일 수정까지
```

## 7. 무엇이 무엇을 강제하는가

| 규칙 | 장치 |
|---|---|
| 루트와 `docs/`의 파일 구조 | `docs-guard.mjs`(PreToolUse)가 생성을 거부, 검사기가 커밋을 거부 |
| 작업자의 살아 있는 문서 편집 금지 | `docs-guard.mjs`가 워크트리 경로에서 거부 |
| 닫힌 작업 파일 수정 금지 | `docs-guard.mjs`가 거부, `--close`가 검사 |
| 예산 파일은 사람만 | `docs-guard.mjs`가 거부 |
| `--no-verify`, 훅 경로 변경 | `docs-guard.mjs`가 Bash 명령을 거부 |
| 예산과 제목 구조 | 검사기. Stop 훅이 실패 시 턴 종료를 막고, pre-commit이 커밋을 막는다 |
| 닫기 커밋에서 BRIEF·ARCH 비증가, 결정 로그 증가 상한 | `--close` |
| "갱신이지 추가가 아니다"의 의미, ARCH가 현재 상태인지, 지시 절이 필요한 만큼인지, 작업 기록의 충실도 | 강제 불가. 예산 상한으로만 압박한다. |

## 8. 도입하기

1. 이 규약을 `docs/README.md`로, `check-docs.mjs`와 `docs-guard.mjs`를 `scripts/`로, `pre-commit`을 `.githooks/`로 복사한다. `.claude/settings.json`에 훅 설정을 합친다(스킬의 `assets/hooks.json`). `git config core.hooksPath .githooks`를 건다. SessionStart 훅이 새 클론에서도 같은 설정을 건다.
2. 계획 문서를 나눈다. 프로세스 구조, 데이터 모델, 모듈 표, API 표는 ARCH로. 끝난 단계의 시나리오와 경위, 측정 기록은 `decisions.md`와 작업 파일의 보고 절로. PLAN에는 지금 단계와 다음 단계만 남기고 세 절 구조로 다시 쓴다.
3. 작업마다 `docs/log/<작업>.md`를 만들고 지시문을 지시 절로, 보고서를 보고 절로 옮긴다. 첫 줄은 `상태: 닫힘`.
4. CLAUDE.md에서 변경 이력 문단을 README로, 도구·환경 변수·명령 이름이 든 줄을 `testing.md`로 옮긴다. 다음 한 줄을 넣는다.

   > 문서를 만들거나, 작업을 맡기거나, 단계를 닫을 때는 `docs/README.md`를 따른다.

5. BRIEF 표에서 뒤집힌 문장을 `decisions.md`로 옮기고 행을 500자 이하로 다시 쓴다.
6. 검사 스크립트를 돌려 통과를 확인한다. ARCH가 40,000자를 넘으면 API 표를 한 줄 행으로 줄이고 설명을 코드 주석으로 보낸다. 예산을 올리지 않는다.
