# coordinate: 나누고, 맡기고, 취합한다

메인 세션은 계획과 판단을 지킨다. 구현은 하위 세션이 한다.
메인은 직접 코드를 쓰지 않고, 공통 기반 커밋과 취합만 한다.

## 핵심 원칙

독립적인 업무를 명확한 결과와 책임 소재를 가진 병렬 하위 세션으로 분할한다.
하위 세션은 자기 범위 밖의 문제를 만나면 직접 고치지 않고 보고하며, 메인이 담당 세션에 전달한다.
결과가 계획을 바꾸거나 스스로 해결할 수 없으면 보고한다.
메인은 최종 결과를 통합하고 확인한다.

## 불변 규칙

- 작업자는 반드시 `start_session`으로 만든 하위 세션이다. 서브에이전트(Agent 도구)로 작업자를 띄우지 않는다. 하위 세션 안에서 서브에이전트를 쓰는 것은 자유다.
- `start_session`을 쓸 수 없는 환경이면 멈추고 사용자에게 알린다. 서브에이전트로 대신하지 않는다.
- 코드를 쓰는 하위 세션은 각자 워크트리를 쓴다. 한 파일의 소유자는 한 세션뿐이다.
- 하위 세션은 main(기준 브랜치)에 직접 병합·푸시하지 않는다. 자기 브랜치에 커밋만 한다.
- 메인은 사용자가 승인한 경우에만 하위 브랜치를 병합한다.
- 하위 세션의 규칙은 지시문이 아니라 gudals 플러그인의 coordinate mod의 훅이 주입하고 강제한다. mod가 로드되지 않은 환경이면(6단계의 로드 확인이 실패하면) 사용자에게 알린다.

## 0. 쓸지 판단한다

> 작업마다 "다른 작업의 결과 없이 끝낼 수 있고, 다른 작업과 같은 파일을 건드리지 않는가?" 예 → 나눈다.

- 독립적인 작업이 2개 미만이면 나누지 않고 이 세션에서 한다.
- 공통 기반 없이는 아무것도 시작할 수 없으면, 기반부터 만들고(3단계) 다시 판단한다.
- 하위 세션은 최대 4개. 그 이상이면 묶거나 차수로 나눈다(9단계).
- 앞 작업의 결과(이름, 앵커, 산출물)를 봐야 쓸 수 있는 작업은 같은 차수에 넣지 않고 다음 차수로 미룬다.

## 1. 계획을 고정한다

하위 세션은 이 대화를 보지 못한다. 계획 파일이 유일한 공유 맥락이다.

- PRD, plan, todo 파일이 있으면 그것을 기준으로 삼는다.
- 없으면 대화에서 결정된 것만 추려 `docs/plan.md`(또는 프로젝트 관례 위치)에 쓴다: 목표, 결정된 사항과 이유, 범위 밖, 공유 제약.
- 대화에서 결정되지 않은 것을 계획에 지어 넣지 않는다. 열린 질문으로 적는다.

## 2. 사전 점검

- **이 세션의 작업 폴더가 저장소 루트인지 먼저 확인한다** (`git rev-parse --show-toplevel`과 비교). 다르면 진행하지 않는다.
  - 다르면 `start_session`에 `cwd`를 줘야 한다. 그러면 처음에는 폴더 신뢰를 따로 요구하고, 앱이 자동으로 이어 준 턴에서는 세션 시작이 거부된다. 다음 차수와 실패한 세션 재시작이 모두 사람 손을 거친다.
  - 사용자에게 저장소 루트에서 세션을 다시 열라고 안내한다. 저장소가 없으면 어디를 루트로 둘지 묻고 만든 뒤, 그 폴더로 세션을 옮긴다.
- git 저장소인지, 작업 트리가 깨끗한지, 현재 브랜치가 무엇인지 확인한다.
- 의존성 설치 명령, 테스트·빌드 명령, gitignore된 필수 파일(`.env`, 키 파일 등)을 파악한다.
- 워크트리에는 커밋된 것만 따라가고 gitignore된 파일은 따라가지 않는다. 하위 세션이 무엇을 다시 설치·복사해야 하는지 여기서 정리한다.

## 3. 공통 기반을 먼저 만든다

모두가 기대는 것(공유 타입, API·인터페이스 계약, 폴더 구조, 설정)은 메인이 직렬로 만든다.
병렬로 돌리면 각자 다른 계약을 상상해서 만든다.

**공유 식별자를 계획 파일에 고정한다.** 여러 작업이 서로 참조하는 이름은 모두 여기서 정한다: 앵커 id, 문항·항목 번호 규칙, 파일 명명 규칙, 공유 상수. 하위 세션이 각자 추론해서 맞으면 운이 좋았던 것이다.

**완료 기준을 기계로 검사할 수 있게 만든다.** 빌드·검사 스크립트(누락, 링크, 존재 여부)를 기반에 넣으면 하위 세션이 스스로 완료를 확인한다.

**생성 파일은 커밋하지 않는다.** 빌드 산출물은 gitignore하고, 하위 세션은 각자 다시 빌드해 확인한다. 최종 빌드는 메인이 병합 뒤에 한다. 생성 파일을 커밋하면 병합 때마다 충돌이 난다.

그다음 계획 파일과 기반을 한 커밋으로 남긴다. 커밋하지 않은 것은 하위 세션에 보이지 않는다.

## 4. 분할표를 만든다

작업마다 한 줄씩:

| 이름 | 결과물 | 완료 기준 | 소유 파일·모듈 | 손대지 않을 범위 |
| --- | --- | --- | --- | --- |

- 직무(기획/구현/테스트/리뷰)로 나누지 않는다. 결과물과 소유 범위로 나눈다.
- 완료 기준은 확인할 수 있는 것으로 쓴다: 통과할 테스트, 동작해야 할 명령, 존재해야 할 파일.
- 소유 범위가 겹치면 분할이 잘못된 것이다. 다시 나누거나 합친다.

좋은 분할: `auth` 모듈 구현 / `billing` 모듈 구현 / 관리자 화면 구현 — 계약은 3단계에서 고정됨.
나쁜 분할: 백엔드 설계 / 백엔드 구현 / 테스트 작성 — 서로의 결과를 기다리고 같은 파일을 만진다.

## 5. 사용자에게 한 번에 확인받는다

한 메시지로 묻고, 답을 받은 뒤에는 막힌 경우에만 다시 묻는다.

- 분할표와 차수 계획(차수가 둘 이상이면 무엇이 몇 차수인지)
- 사용자만 줄 수 있는 셋업: 시크릿·env 값, 외부 서비스 접근, 설치 방식
- 기준 브랜치와, 끝나면 메인이 하위 브랜치를 병합해도 되는지
- 하위 세션 모델·권한 모드를 다르게 할지 (기본은 이 세션을 따른다)

## 6. 하위 세션을 띄운다

하위 세션에는 지시문을 길게 보내지 않는다. 작업 명세는 작업 파일에 두고, gudals 플러그인의 coordinate mod의 훅이 하위 세션에 주입하고 강제한다.

### 작업 파일 쓰기

작업마다 `.coord/tasks/<이름>.md`를 쓰고, 계획 파일과 함께 3단계 커밋에 넣는다(이미 커밋했으면 한 번 더 커밋한다). 워크트리에는 커밋된 것만 따라간다.

```
---
owns: src/auth/**, tests/auth/**
base: main
plan: docs/plan.md
---
## 작업
<결과물 한두 줄>

## 완료 기준
- <확인 가능한 기준>

## 손대지 않을 범위
- ... (필요하면 고치지 말고 보고)

## 먼저 할 것
- 셋업: <설치 명령>, <복사할 gitignore 파일과 원본 경로>
```

- `owns`: 쉼표로 구분한 glob. 워크트리 안에서 이 밖의 파일 수정(`.coord/` 포함)은 훅이 막는다. 비워 두면 워크트리 안의 모든 수정이 막힌다.
- 인계 메모 `.coord/notes/<이름>.md`는 `owns`에 쓰지 않아도 그 세션이 쓸 수 있다. 세션마다 파일이 달라서 병합 충돌이 나지 않는다.
- 저장소 밖 경로(세션 스크래치패드, OS 임시 폴더)는 막지 않는다. 검산 스크립트는 거기에 두게 하고, 결과물 폴더에 도구를 커밋하지 않게 한다.
- `base`: 기준 브랜치. 이 브랜치로 옮기는 git 명령을 훅이 막는다.
- 원칙, 강제 규칙, 보고 형식, 인계 메모 안내는 훅이 덧붙이므로 작업 파일에 다시 쓰지 않는다.

### 하위 세션 띄우기

작업마다 `start_session`을 한 번씩, 한 메시지에서 병렬로 호출한다. 먼저 `mark_chapter`로 묶음 제목을 단다.

- `initiation: "user_asked"`, `context: "fresh"`, `use_worktree: true`
- `source_branch`: 작업 파일 커밋이 있는 현재 브랜치. 생략하면 기본 브랜치에서 갈라져 커밋이 빠진다.
- `branch_name`: 반드시 `coord-<이름>`. 훅은 브랜치 이름에서 `coord-<이름>`을 찾아 `.coord/tasks/<이름>.md`와 짝짓는다. 다르면 훅이 켜지지 않는다.
- `name`: `<이름>`
- `background`: 전체 목표 한두 문장과 "작업 명세는 시스템 프롬프트의 coord 섹션에 있다"는 안내
- `prompt`: `.coord/tasks/<이름>.md 작업을 시작하라.` 한 줄이면 된다.

### 로드 확인

세션들이 시작되면, 각 워크트리에서 훅이 남긴 표시 파일을 확인한다. 세션 제목은 신호로 쓰지 않는다(`title`을 주면 앱이 그 제목을 쓴다).

```bash
git worktree list --porcelain | grep '^worktree' | cut -d' ' -f2- | while read -r w; do f="$(git -C "$w" rev-parse --git-path coord-loaded)"; case "$f" in /*|?:*) ;; *) f="$w/$f";; esac; [ -f "$f" ] && echo "loaded: $w ($(cat "$f"))"; done
```

하위 세션 수만큼 `loaded:` 줄이 나와야 한다. 빠진 세션은 브랜치 이름(`coord-<이름>`)과 그 워크트리의 `.coord/tasks/<이름>.md`를 확인하고, 그래도 없으면 사용자에게 알린다.

### 훅이 하위 세션에서 하는 일

| 시점 | 동작 |
| --- | --- |
| 세션 시작 | 브랜치로 작업 파일을 찾고, 워크트리 git 폴더에 `coord-loaded` 표시를 남긴다 |
| 매 요청 | 원칙·소유 범위·강제 규칙·인계 메모·보고 형식·작업 명세를 시스템 프롬프트 섹션으로 붙인다. 압축돼도 사라지지 않는다 |
| Edit / Write / NotebookEdit | 워크트리 안에서 `owns`와 자기 인계 메모 밖이면 거부한다. 같은 저장소의 다른 체크아웃도 거부한다. 저장소 밖은 허용한다 |
| Bash | git push, merge, rebase, 기준 브랜치로 checkout·switch, reset --hard, 브랜치 생성·이름 변경·강제 삭제, worktree add를 거부한다 |
| wrap_up | recap이 `DONE:` / `BLOCKED:` / `PLAN-CHANGE:`로 시작하지 않으면 거부한다. 메인 알림은 recap이 먼저 오기 때문이다 |
| 턴 종료 | 마지막 메시지 첫 줄도 같은 형식이 아니면 한 번 되돌려 보낸다. 백그라운드 작업을 기다리는 중이면 막지 않는다 |

Bash로 파일을 쓰는 것(리다이렉션, 스크립트)은 막지 못한다. 소유 범위는 8단계 diff 확인으로 한 번 더 본다.

## 7. 진행 중

- 메인은 기다린다. 폴링하거나 "끝났나요?"를 보내지 않는다. 하위 세션이 턴을 끝내면 앱이 메인을 깨운다.
- 알림은 400자에서 잘린다. 첫 줄의 상태만 보고 판단하고, 보고 전문이 필요하면 `list_events`를 `limit` 2–4로 불러 그 세션의 마지막 이벤트만 읽는다. 인계 정보는 그 세션 브랜치의 `.coord/notes/<이름>.md`에 있다.
- `BLOCKED`: 메인이 답할 수 있으면 `SendMessage`로 그 세션에 답한다. 사용자만 답할 수 있으면 사용자에게 묻고, 답을 그대로 인용해 전달한다.
- 범위 밖 문제 보고: 담당 세션에 전달한다. 담당이 없으면 사용자에게 알린다.
- `PLAN-CHANGE`: 다른 세션에 영향이 있으면 사용자에게 확인받고, 계획 파일을 고쳐 커밋한 뒤 영향받는 세션에 알린다. 하위 워크트리의 작업 파일은 이미 갈라져 있어 바뀌지 않으므로, 바뀐 내용은 `SendMessage`로 직접 보낸다.
- 한 세션이 실패해도 나머지는 계속 둔다. 실패한 작업만 다시 브리프하거나 사용자에게 넘긴다.

## 8. 취합하고 확인한다

모든 세션이 `DONE`이거나 처리 방향이 정해지면:

1. 보고를 믿지 말고 각 브랜치의 diff와 완료 기준을 직접 확인한다.
   - 브랜치는 앱이 접두·접미어를 붙인 이름이다. `git branch --list '*coord-*'`로 찾는다.
   - `git diff --name-only <base>...<브랜치>`의 파일이 작업 파일의 `owns`와 `.coord/notes/<이름>.md` 안에 있는지 본다. Bash로 쓴 파일은 훅이 막지 못했으므로 이 확인이 마지막 방어선이다.
2. 병합 승인이 있으면 의존이 적은 순서로 `refs/heads/<브랜치>`를 하나씩 병합하고, 병합할 때마다 테스트를 돌린다. 충돌이 소유 범위 위반에서 온 것이면 고치지 말고 사용자에게 보고한다.
3. 승인이 없으면 병합하지 않고 브랜치 목록과 각 상태를 보고한다.
4. 메인이 최종 빌드를 하고, 결과물을 직접 확인한다(테스트, 브라우저, 출력물).
5. 다음 차수가 있으면 9단계로 간다. 없으면 `.coord/` 폴더를 지우는 커밋을 제안한다.
6. 최종 보고: 작업별 결과, 확인하지 못한 것, 남은 일, 하위 세션 링크. 보관(archive)은 사용자가 원할 때만 한다.

## 9. 다음 차수

앞 차수의 결과를 봐야 쓸 수 있는 작업은 차수를 나눠 돌린다. 앞 결과를 보고 쓴 작업 파일이 품질이 더 좋다.

1. 앞 차수를 모두 병합하고 최종 빌드까지 확인한다.
2. 병합된 결과에서 실제 이름·앵커·산출물을 보고, 계획 파일의 공유 식별자를 갱신한다.
3. 다음 차수의 작업 파일을 쓰고 커밋한다. 앞 차수의 작업 파일과 인계 메모는 지우지 않고 둔다.
4. 6단계부터 반복한다. `source_branch`는 병합이 끝난 지금 브랜치다.

이 세션의 작업 폴더가 저장소 루트이면, 앱이 자동으로 이어 준 턴에서도 다음 차수를 바로 띄울 수 있다. 사용자에게 다시 묻지 않는다(5단계에서 차수 계획까지 확인받는다).
